# ワークフロー規律の必要性（Why）


## ビジネス要件

### 問題の本質

Phase 1で作成したルール（language-policy, commit-message, journal-writing）は、
**ワークフローを経由せずに直接実装された**。

これにより：
- business/spec/archiが空のまま
- 意思決定の背景（Why）が散在
- 仕様（What）が不明確
- 設計（How）が文書化されていない

### なぜワークフローが必要か

#### 1. 意思決定の透明性
- **Why**が明確でないと、将来「なぜこうなったか」がわからない
- 修正や変更時に判断基準がない
- AIに背景を説明できない

#### 2. 段階的な検討
- backlog → business → spec → archi の流れで**段階的に深掘り**できる
- 各段階で立ち止まって考える機会を作る
- 早期に問題に気づける

#### 3. 再利用性
- business/spec/archiが揃っていれば、**同様のタスクで参照できる**
- ドキュメントが資産になる
- AIが過去の判断を学習できる

#### 4. vibe codingの実現
- 思考を整理してから実装することで、**迷いなくコーディングできる**
- ワークフローが思考のフレームワークになる
- 作業が気持ち良く進む

### 誰のため？

- **未来の自分のため**: 過去の判断を思い出せる
- **AIのため**: 文書化された意図を読める
- **チーム化の可能性**: 将来的に他者と協働する際の基盤

### ビジネス価値

このテンプレートの目的は「気持ちよくvibe codingをする」こと。

ワークフローを守ることで：
- 思考が整理される → vibe coding実現
- ドキュメントが自然に蓄積される → 資産化
- AIとの協働が最適化される → 効率化

## 見直し条件

- ワークフローが形骸化し、逆に生産性を下げている場合
- より良いワークフローが見つかった場合
- 個人開発からチーム開発に移行する場合
