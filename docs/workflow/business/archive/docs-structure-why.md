# ドキュメント構造再設計の必要性（Why）

## なぜ再設計が必要か

### 問題1: 役割の混在

**現状**:
- backlog/roadmap が workflow/ 配下にある
- これらは「大きな政策方針」なのに「具体的な実装作業」と同階層

**問題**:
- 概念的な混乱
- workflow の本来の目的（business/spec/archi で深掘り）が不明確
- 大方針と実装タスクが区別できない

**ビジネス価値への影響**:
vibe coding を実現するには、**思考のレベル分け**が重要。
- 大きな方針を考える時
- 具体的な実装を考える時

これらが混在すると思考が散漫になる。

### 問題2: トークン消費

**現状**:
- ファイル内に `**Status**: wip` を記述
- AIがステータス確認のためにファイルを開く必要

**コスト**:
- 1ファイルあたり約100-500トークン消費
- 9ファイル（business/spec/archi × 3ルール）= 約1000トークン
- ステータス確認のためだけに消費するのは非効率

**ビジネス価値への影響**:
- AIとの協働コストが高い
- トークン制限に早く到達
- 開発速度の低下

### 問題3: 視認性

**現状**:
- ファイルを開かないと wip/adr がわからない
- `ls` や `tree` で状態が見えない

**ユーザー体験への影響**:
- どのドキュメントが確定版かわからない
- 古いドキュメントを参照してしまうリスク
- ファイル管理のストレス

## なぜフォルダ管理か

### メリット1: ゼロトークンでステータス確認
```
ls docs/workflow/business/adr/
→ 確定版が一覧表示、ファイルを開く必要なし
```

### メリット2: 視覚的に明確
```
business/
  wip/           # 作成中が一目瞭然
  adr/           # 確定版が一目瞭然
  archive/       # 古い版が一目瞭然
```

### メリット3: 操作がシンプル
```bash
# wip → adr への移行
mv business/wip/xxx.md business/adr/xxx.md
```

## ビジネス価値

この再設計により：
1. **思考の整理**: 大方針と実装タスクが明確に分離
2. **トークン削減**: ステータス確認がゼロトークン
3. **vibe coding**: ストレスフリーなドキュメント管理
4. **AI協働**: 効率的なコンテキスト読み込み
