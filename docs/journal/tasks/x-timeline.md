# タスク: X のタイムラインを封印

## 実施したタスク

### 完了
- X 対応: ホーム（/home）と話題を検索（/explore）の中央カラムをグレーの封印パネルに、右カラム（トレンド・おすすめユーザー）を全ページで非表示
- 通知・DM・プロフィール・個別ポスト（他人のものも）・検索・設定・ポスト作成は自由
- 無効化・夜間モード・夜間の封印は YouTube と共通
- 封印の付け外し処理を `overlay.ts` に共通化、content script をサイトごとに分割（`youtube.content.ts` / `x.content.ts`）
- URL 判定のテスト追加（計12件）、README・CLAUDE.md・coding.md 更新

## 技術的決定事項

### TD-1: 封印の範囲
- **決定**: 無限に流れてくるもの（ホーム・話題・右カラム）だけ。それ以外は触らない
- **経緯**: 最初は「通知・DM・自分のポスト以外すべて封印」で設計しかけたが、ユーザーから「シンプルに、タイムライン中心に時間を吸われる概念を禁止」と方針転換。他人のポストは丸ごと通す

### TD-2: 判定の置き場所
- **決定**: URL 判定だけ JS（`<html>` にフラグ属性）、隠す処理は CSS
- **理由**: CSS から URL は見えない。「JS で判定しない」規則の例外として、ページ単位に限定して coding.md に明記

### TD-3: 要素の目印
- **決定**: `<main>` と `main ~ aside`（旧 UI の `data-testid` も併記）
- **理由**: 2026年の X は作り直されていて `data-testid` が見当たらず、クラスは Tailwind で不安定。ランドマーク要素が一番壊れにくい

## ミス・想定外
- 「X いこう」を X への告知投稿と誤解し、投稿文と画像を作ってしまった。実際は X にも封印を広げる話だった
- X の DOM が想定（`data-testid` の列）と違った。実ページで確認してから CSS を書いて正解だった

## 追記: レイアウトを崩さない形に作り直し
- ユーザー指摘「ロード時間が長く、レイアウトがめっちゃ変わる。パワー系の解決では？」→ その通りだった
- ログイン状態は旧 UI（`data-testid` あり）で、`<main>` が両カラムを包んでいた。`main > *` を消したため全体が1枚のグレーに
- ユーザーの Chrome（Claude in Chrome、許可済み）で構造だけ確認し、タイムラインの一覧だけ・右カラムのモジュールだけを消す形に変更。幅・タブ・投稿欄・検索窓は維持
- ロード時間: 初回の /home でタブが固まる現象が1回あったが再現せず（夜間で封印は非適用の状態）。以降は DOMContentLoaded 80〜110ms で通常どおり
- 反省: ログアウト状態のページだけ見て書いた。対象の実画面を見てから書く。調査中の誤クリックでホームの選択タブが変わったので元に戻した
