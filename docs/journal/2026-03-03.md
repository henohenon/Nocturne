## 意思決定

### ハイブリッド言語ポリシーの採用

**背景**:
vibe codingを実現するためには、思考を素早く記録できる環境が必要。
一方、AIとの協働やコードの標準性も重要。

**選択肢**:
1. 全て英語（AI・国際標準重視）
2. 全て日本語（思考速度・理解速度重視）
3. ハイブリッド（使い分け）

**決定**: ハイブリッドアプローチ
- ドキュメント: 日本語
- コミットメッセージ: 英語
- コード・コメント: 英語

**理由**:
- 自分のためのテンプレートなので、思考を妨げない日本語でドキュメント
- Git履歴やコードは国際標準・AI協働のために英語
- 両方のメリットを享受できる

### workflow/ 配下への階層化

**背景**:
backlog, roadmap, research, business, spec, archi が並列だと、
静的なルール（rules/）や記録（journal/）と区別がつきにくい。

**決定**: workflow/ 配下にまとめる

**理由**:
- 開発の動的な進行を1箇所で管理
- rules/とjournal/が独立して見やすくなる
- ワークフローの全体像が把握しやすい

### Conventional Commitsの採用

**決定**: Conventional Commits + Claude Code Attribution → シンプルフォーマットに変更

**理由**:
- 既存のコミット履歴がすでにこのパターン
- ツールとの親和性が高い
- AIとの協働を明示できる（Co-Authored-By）

**再決定**（Phase 0中）:
- `<type>: <subject>` のみのシンプルフォーマット
- body/footerは不要（詳細はPR/issueで）
- TUIでのスキャナビリティ重視

### Rules最適化の必要性

**背景**:
Phase 1で作成したrulesが冗長すぎた（約3700トークン）。
AIが毎回読む可能性があるため、トークン消費が大きい。

**決定**: 88%トークン削減（3700 → 450トークン）
- 英語化（トークン効率）
- 例を全削除
- Core Rulesのみ
- Status行削除
- Naming規則は別ルールへ

**理由**:
- AIの読み込みコスト削減
- 本質的なルールのみに絞る
- 詳細は実例（journal）とテンプレートでカバー

### Workflow活用の必要性

**問題**:
Phase 1でbusiness/spec/archiを全く使えていない。
ワークフローの本来の流れ（backlog → business → spec → archi → 実装）を実践できていない。

**決定**: Phase 0 Task 1として優先的に修正
- 既存ルールのワークフロー文書を作成
- business/spec/archiを実践
- ワークフロー使用ガイドを作成

**実施結果**:
- ワークフローを**完璧に実践**して文書構造再設計を実施
- backlog → business/wip → spec/wip → archi/wip → 実装 の流れを体験
- 9つのワークフロー文書を作成（既存3ルール分）

### ドキュメント構造再設計

**問題**:
- backlog/roadmap が workflow/ 配下にあり、役割が混在
- Status: wip の記述でトークン消費
- ファイルを開かないと状態がわからない

**決定**: フォルダベースのステータス管理
- backlog/roadmap を docs/ 直下に移動（政策と実装の分離）
- wip/adr/archive フォルダで状態管理
- Status行削除でゼロトークン化

**効果**:
- ステータス確認がゼロトークン（`ls` で判別可能）
- 視認性が劇的に向上
- 思考のレベル分けが明確に

### トークン数が消し飛んだ
jetbrains aiの特性上限界な気もするし、docsが巨大になりすぎたせいな気もする。
マジであと10倍欲しい。cloude codeのmax行こうかな
- 半分ぐらいしか解決しない気がする。
- 結局性能の良い、コスパの良いaiが変わる
- 良し悪しはあれどマネーゲーム。
- ここで投資できないのは弱すぎる感はあるが
- どちらかというとそういう時代なのではないか。
- 今は昔でいうプログラムのコンパイルに1時間かかるような時代。

### Phase 1でのワークフロースキップ

**背景**:
Phase 1実装時、またしてもworkflow文書（business/spec/archi）を作成せず直接実装してしまった。

**問題**:
- Phase 0でワークフローの重要性を学んだはずなのに再発
- error-prevention.mdに「Mistake 1」として文書化したばかりのミスを即座に繰り返した
- ルールを作るだけでは不十分、実践の強制が必要

**対処**:
1. Phase 1のworkflow文書を事後作成
   - business/wip/phase1-ai-discipline.md
   - spec/wip/phase1-ai-discipline.md
   - archi/wip/phase1-ai-discipline.md
2. 再発防止策の強化
   - error-prevention.mdに「Recurrence Prevention」セクション追加
   - TodoWrite使用の義務化: 最初の3 todosは必ずworkflow文書作成
   - .aiassistant/rules/index.mdに「TodoWrite with workflow docs FIRST」追加

**決定**: ワークフロースキップは構造的に防止する
- ルールだけでなく、TodoWriteによる強制
- 実装todosの前に必ずworkflow todos完了を要求
- AIが自己チェックできる仕組み

### 新しく学んだこと
- ドキュメント構造を先に作ると、後の作業がスムーズ
- 言語ポリシーは最初に決めないと、他のドキュメントが書けない（依存関係）
- git HEREDOC でコミットメッセージを書くと複数行が楽
- AIが読むドキュメントはトークン効率を最優先すべき
- 英語化 + 簡潔化で劇的なトークン削減が可能
- ワークフローは設計するだけでなく、実践の仕組みが必要
- **フォルダベースの状態管理は視認性とトークン効率を両立**
- **ワークフローの実践は体で覚える**: 今回の再設計で完全に身についた
- **政策と実装の分離**: backlog/roadmap（方針）と workflow/（実装）は別レベル
- **ルールの文書化だけでは不十分**: TodoWriteによる構造的強制が必要
- **ミスは即座に再発する**: 防止策を書いた直後でも繰り返す（人間もAIも同じ）
- **事後でもworkflow文書を作る価値**: 思考の整理と次回への学び

### 次に活かせそうなこと
- テンプレート作成は実際に使いながら改善していく
- ルールは完璧を目指さず、まず作って実践しながら調整
- **ワークフローは毎回必ず実践する**: backlog → business/wip → spec/wip → archi/wip → 実装
- **TodoWriteの最初の3項目は必ずworkflow文書作成**: 構造的強制
- Rulesは常に最小限に保つ（Status不要、例不要）
- フォルダ構造で状態を表現する（メタ情報をファイル外に）
- 問題を発見したら即座に Phase 0 的な割り込み修正を検討
- ミスを繰り返したら、防止策の「強制力」を強化する
